# 変更作業

着手時に、依頼から期待する結果と確認方法を定める。作業範囲が変わったら、完了条件も更新する。

- 既存のコメントは勝手に削除しない。変更に不要なコメントはそのまま保持する。
- コードから読み取れない設計判断や制約は、該当箇所のコメントに理由を残す。処理を言い換える説明や検討過程は書かない。
- 不具合修正では、症状を隠す対症療法的な回避策を加える前に根本原因を特定し、原因が存在する箇所を必要十分な変更で直す。
- 原則として、一つのまとまった変更ごとにPRを分け、無関係な変更を混ぜない。軽微でCIが失敗する可能性が低い変更は、PR作成後にauto-mergeまで進める。
- PRの作成・更新時は、[PRテンプレート](../.github/PULL_REQUEST_TEMPLATE.md)に従ってタイトルと本文を記述する。
- 変更のスコープが変わったら、PRのタイトルと本文を最終的な変更内容に合わせ、コミットも意味のある変更単位に整理する。独立した変更は別PRへ分け、依存関係のある変更を分ける場合はStacked PRを使う。
- 検証の再試行は、コードや設定の修正、一時的な環境障害など、結果が変わる根拠がある場合に限る。同一原因の失敗が続き、追加の進展がない場合は再試行を止め、失敗内容と必要な対応をユーザーへ報告する。

## 完了条件

- 依頼された動作・成果物を満たし、仮実装や依頼範囲内の未対応事項が残っていない。
- 変更の影響に応じた検証を実施し、変更に起因する不具合を修正して該当する検証を通している。UIの動作変更では対象の操作から表示結果まで確認する。文章だけの変更では内容・参照先・書式を確認し、アプリのテストやビルドは不要。
- 最終差分を確認し、無関係な変更や作業前から存在した他者の変更を混ぜていない。設計意図や責務境界が変わる場合は、対応するドキュメントも整合している。
- PR作成・公開・デプロイまで依頼されている場合は、その到達点と結果を確認している。承認や外部環境が必要で進められない場合は、完了とはせず未完了部分と必要な対応を明示する。
- 最終報告に変更結果、検証結果、残る制約を記載する。検証できなかった項目は、理由と未確認の範囲を区別して伝える。
