# 変更作業

- 既存のコメントは勝手に削除しない。変更に不要なコメントはそのまま保持する。
- コードから読み取れない設計判断や制約は、該当箇所のコメントに理由を残す。処理を言い換える説明や検討過程は書かない。
- 原則として、一つのまとまった変更ごとにPRを分け、無関係な変更を混ぜない。軽微でCIが失敗する可能性が低い変更は、PR作成後にauto-mergeまで進める。
- 変更のスコープが変わったら、PRのタイトルと本文を最終的な変更内容に合わせ、コミットも意味のある変更単位に整理する。独立した変更は別PRへ分け、依存関係のある変更を分ける場合はStacked PRを使う。
- 検証の再試行は、コードや設定の修正、一時的な環境障害など、結果が変わる根拠がある場合に限る。同一原因の失敗が続き、追加の進展がない場合は再試行を止め、失敗内容と必要な対応をユーザーへ報告する。
