# コードレビュー

レビューの目的は、理論上の完全性ではなく、実際のユーザー体験と変更の安全性を高めることである。

- レビュー対象は、原則として今回の差分によって新しく発生した問題に限る。既存の問題、機能追加の提案、PRの目的外の改善は指摘しない。
- 指摘前に、PR本文、関連Issue、設計ドキュメント、既存テスト、実際の呼び出し元を確認する。明示された仕様、サポート範囲、コードベースの前提を、一般論だけで不具合扱いしない。
- 原則として、次のいずれかに該当する問題だけを指摘する。
  - サポート対象の利用経路または運用経路を壊す
  - ユーザーデータの消失・破損を起こす
  - 具体的な攻撃経路を持つセキュリティ、決済、認可の問題を起こす
  - リポジトリで実行されるCIまたは本番ビルドを失敗させる
  - ユーザーが認識できる明確なUX低下を起こす
- 指摘には、発生条件、通常の操作または運用からの到達経路、ユーザー影響、差分中の原因を具体的に示す。いずれかを説明できない理論上の可能性は指摘しない。
- テスト、CI、ビルド、ランタイムエラーを指摘する場合は、リポジトリの実際のコマンドで再現するか、失敗が確実である根拠を示す。未確認のツール挙動やテスト間干渉を、再現済みの不具合として扱わない。
- 低確率の競合、非標準的な入力、未対応ブラウザ、未使用の通貨・API・プロバイダー固有仕様、過去に非対応と決めた形式は、実際の要件、障害実績、サポート表明、既存テストによる根拠がない限り指摘しない。
- フロントエンドでは、防御コードの網羅性よりも、操作の分かりやすさ、応答性、フィードバック、復旧可能性を優先する。クライアントだけで完結する異常入力への防御は、主要操作や永続化データへ影響しない限り要求しない。
- エラー処理、ログ、通知は、その欠落によって主要操作が不可能になる、データが失われる、またはユーザー影響のある障害を検知・復旧できなくなる場合だけレビュー対象とする。分類、情報量、網羅性だけの改善は指摘しない。
- PRの目的を達成している簡潔な実装を許容する。将来の可能性、完全な一般化、単一用途の抽象化、使われていない拡張性を要求しない。修正案も、確認できた問題を解消する最小範囲に留める。
- 再レビューでは、直前の修正が作ったリグレッション、または以前の判断を覆す具体的な新証拠がある重大問題だけを新規に指摘する。修正箇所から隣接する境界ケースを連鎖的に掘り下げない。
- メンテナーが仕様、非対応範囲、または意図的な設計判断として却下した論点は、新しい具体的証拠がない限り再度指摘しない。
