# フロントエンド設計

この文書は、React コンポーネントとクライアント状態の責務境界を定める。

## コンポーネントの責務

- コンポーネントは、取得済みの状態を表示へ変換し、ユーザー操作を状態操作へ渡すことを主な責務とする。
- 単一の表示領域に閉じるタイマーやブラウザイベントなどのライフサイクル処理は custom hook にまとめる。atom が所有する状態に伴う処理や複数の表示領域から参照される処理は atom effect にまとめる。
- 保存、削除、選択、リセットなど、複数の状態を一貫して更新する操作は write atom またはドメイン関数にまとめる。
- JSX と状態操作が同じファイルで増え続ける場合は、表示領域または独立した操作単位でコンポーネントを分割する。
- 利用箇所が限られるコンポーネントには、現在使う props と設定だけを持たせ、未使用の拡張点や `displayName` を先回りで追加しない。
- 親コンポーネントが状態や操作を利用せず子へ転送するだけになる場合は、利用するコンポーネントが atom を直接参照する。汎用的な表示コンポーネントへ値やイベントを渡すことはこの限りではない。
- 表示コンポーネント専用に複数の状態を束ねる view atom は作らず、コンポーネントが必要な atom を個別に購読する。複数箇所で使うドメイン上の計算は derived atom として共有する。
- controller hook を設ける場合は単一の接続境界または責務に限定し、複数の表示領域が使う状態と操作を一つの戻り値へ集約しない。

## 入力境界と検証

- ユーザー入力、クリップボード、通信応答、永続化データは信頼せず、状態反映や保存の境界でドメインの不変条件を検証する。
- 画面固有の要件がない限り、数値入力の `NaN` や `Infinity` をクライアントの各入力で個別に防御しない。永続化する値はサーバー境界で検証する。ただし任意のユーザー入力を `Number.parseInt` した際に数値でない値が来る可能性は想定する。
- アプリの通常操作と正規のデータ移行では生成されない不正形式や未知バージョンは、画面固有の状態や復旧操作へ変換しない。読み取り境界で例外にし、共通のエラー処理へ委ねる。
- リポジトリで管理する設定値やテスト定数は開発者が所有する入力として扱い、必須値の確認と必要な型変換に留める。誤設定が権限やデータを損なわず、利用箇所で明確に失敗する場合は、想定上の表記揺れまで実行時検証しない。
- 既存の完了状態や下流APIが同じ条件を保証している場合、追加のpollingや重複したガードを置かない。防御は入力の信頼境界と失敗時の影響に比例させる。
- 基盤の制約で完全な検証やキャンセルを直接表現できない場合、権限や他ユーザーのデータに影響しない限り、複雑なデータモデル変更や履歴操作で模倣しない。読み取り時の防御と復元経路で安全に扱う。

## 状態の配置

- 複数の表示領域、非同期処理、React のライフサイクル外の処理から参照される状態は Jotai の atom に置く。
- atom から計算できる値は新たな状態として保持せず、derived atom として表現する。
- derived atom は、再利用するドメイン上の計算、購読範囲の縮小、書き込み可能な atom を readonly として公開する境界のいずれかを担う場合に使う。
- write atom は、atom の読み取りや複数 atom の一貫した更新が必要な操作に使う。
- 画面や機能に閉じた atom の store 範囲は、実際のインスタンス数とライフサイクルに合わせる。同時に複数存在する場合は `Provider` で分離し、単一インスタンスの module atom は画面破棄時に一時状態を初期化して再表示へ漏らさない。
- 入力ライブラリや外部データ hook が管理する状態は、そのライブラリを正本としてよい。atom と接続する処理は専用の controller hook など一箇所に限定する。
- 単一コンポーネント内で完結し、他の状態と同期しない一時的 UI 状態はローカル状態とする。付随するライフサイクル処理は専用の custom hook に閉じ込める。
- 機能専用の `Provider` は、同時に存在する複数インスタンスまたは独立したライフサイクルが必要な場合に限る。store を分けるとアプリ全体の atom へ直接依存できなくなるため、その接続コストも含めて導入を判断する。必要な場合もグローバル atom の購読を重複させず、境界を越える値を最小限にする。
- 非同期操作の実行中状態は操作と対象ごとに分離し、操作開始時に write atom または操作元のローカル状態で同期的に確保する。同一対象の二重実行だけを防ぎ、無関係な対象や操作を一括で無効化しない。
- ボタンの無効化と処理中表示に使うローカル状態を、同じ値の `ref` にも重複して保持しない。コンポーネントの再マウントや複数の呼び出し元をまたぐ排他が必要な場合は、操作境界の atom で実行中状態を管理する。
- 外部データの応答を状態へ反映する場合は、操作開始時の所有者と対象 ID を保持し、反映直前の認証セッションと選択へ照合する。以前のセッションや選択に対する遅延応答を、現在の状態や通知へ適用しない。
- 購読がページや範囲の一部だけを監視する場合、変更操作の結果が購読から通知されるとは限らない。成功した対象は一件ごとに取得元のローカル状態へ反映し、途中失敗後の再試行には未完了の対象だけを残す。
- 入力モデルで省略が削除を意味するフィールドを永続化するときは、古い省略可能フィールドを確実に削除する。完全な文書で置換する場合は、transaction または revision の照合で並行更新を検出する。
- フォームライブラリを atom へ接続するときは、ライブラリの戻り値全体を保持せず、状態遷移に必要な取得・リセット・送信操作と最小限のスナップショットだけを公開する。

## Effect の扱い

- `useEffect` と `useLayoutEffect` は、宣言的な表示だけでは表現できない外部システムとの接続に限定する。
- 状態や関数を別の状態へ転記する同期は、正本を増やして更新順序への依存を生むため最後の手段とする。追加する前に、元の atom への直接依存、derived atom、単一の write atom、純粋関数への引数渡し、store 作成時の初期化で表現できないか確認する。
- 同期を許容するのは、外部ライブラリが状態の正本を持つ場合に限る。同期する値と命令的な操作は必要最小限にし、接続境界を一箇所へ集約して業務上の分岐を置かない。
- React effect と atom effect の cleanup では、購読、イベントリスナー、タイマーなど、その effect が作成したリソースを解放する。
- 状態を保持する atom に専用の effect が対応する場合は、`withAtomEffect` などで一つの atom として公開する。利用側に状態 atom と effect atom の両方を購読させない。
- 非同期の外部入力は、取得開始前ではなく状態へ反映する直前に前提条件を再確認する。確認と反映は一つの write atom またはドメイン操作にまとめる。
- 同じグローバルイベントを複数インスタンスが監視する場合、保護対象の状態を実際に持つインスタンスだけがイベントを処理済みにする。対象がないインスタンスは、後続のハンドラーを妨げない。
- 操作のたびに表示時間を延長するフィードバックは、表示中かどうかだけで再実行を表現しない。操作ごとのトリガーを状態に含めるか既存のタイマーを明示的に解除し、最新の操作を起点にタイマーを張り直す。

## 機能ディレクトリ

- 一つの機能に状態、外部 hook との接続、表示部品が複数ある場合は、それらが扱う内容ごとのディレクトリへまとめる。`state`、`runtime`、`ui` のような技術上の役割だけでディレクトリを分けない。
- primitive atom、derived atom、write atom、atom effect は、その状態や操作が属する内容のファイルへコロケーションする。atom の種類ごとにファイルを分けず、同じ内容の状態遷移を複数ファイルへ散らさない。
- 一つの内容が独立して変更される複数の振る舞いを持つ場合は、振る舞いごとのファイルへ分ける。一方で、複数の内容を扱う状態、サービス、副作用の集約ファイルを作らない。
- 外部 hook との接続は、接続先の内容と同じ場所へ置き、業務上の状態遷移を持たせない。
- 表示部品も、それが操作または表示する内容と同じ場所へ置く。フォームや一覧など複数部品で構成される領域は内容名のサブディレクトリを作り、機能配下へ全ファイルを平坦に並べない。
- 同じ機能の複数インスタンスが同時に存在し得る場合、React 外に退避する一時データと `form` 属性などの DOM 接続 ID も、安定したインスタンスキーで分離する。
